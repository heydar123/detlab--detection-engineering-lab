- **Status.** The first eight rules are `stable`: they went through the most rounds of testing and tuning. The other 24 are `experimental`: newer, with less time against noise.
- **Made-up logs.** Alerts on the synthetic logs (seed 7, 14 days) without exclusions, then with them, and how many of those alerts were false alarms.
- **Real recordings.** How many recordings expected this rule and how many it fired on, and how many alerts it raised on all the recordings (and how many of those belong to the recorded attack).
- **Sigma.** Whether the rule's logic could be exported to Sigma and converted to Splunk and Microsoft Sentinel queries. Nothing was run on a live SIEM; see [sigma/INDEX.md](../sigma/INDEX.md).

## Rule types

| Type | Fires when | Rules |
|---|---|---|
| `match` | one event that matches the filter raises an alert (optionally at most one alert per entity in a pause) | 20 |
| `threshold` | N matching events for the same group inside a time window | 2 |
| `distinct_threshold` | N different values of one field (for example accounts or hosts) for the same group inside a window | 4 |
| `sum_threshold` | the sum of a number field (for example bytes sent) for the same group passes a limit inside a window | 1 |
| `beaconing` | events from one group repeat at a steady rhythm, the way a program checking in with its controller does | 1 |
| `first_seen` | a value (for example a network provider) is seen for the first time for an account, after a learning period | 1 |
| `impossible_travel` | successful sign-ins from two countries closer together in time than a person could travel | 1 |
| `fail_then_success` | enough failures, then a success, for the same group inside a window | 2 |
